| DEC-020 | Android screen capture pipeline | **MediaProjection → VirtualDisplay → codec input `Surface` → hardware H.264 `MediaCodec` (byte-buffer output) → JNI (`byte[]`) → Go core** (Spike 03 ratified; evidence: [results](spikes/03-android-mediaprojection-encoder-results.md)). **Bootstrap order is consent-first:** Activity `createScreenCaptureIntent()` → foreground service (`type=mediaProjection`) → `getMediaProjection` + `registerCallback` → `createVirtualDisplay`; starting the FGS before consent throws `SecurityException` on Android 15 at **both** targetSdk 34 and 35 (appop `project_media`, which only consent grants, is the gate). **Capture scope is requested explicitly** — the Android 15 dialog defaults to "A single app", so full-screen mirroring requires selecting "Entire screen" (`dumpsys media_projection`: `TYPE_SCREEN_CAPTURE`). **Codec chosen by capability** (`isHardwareAccelerated` + `areSizeAndRateSupported`), H.264 High primary (`c2.qti.avc.encoder` class), HEVC optional (present but unmeasured), **AV1 excluded** (software-only ≤ 1920 px on target devices). **Capture is damage-driven at panel refresh** (119–120 fps measured at 1080×2400 on SM7475/Android 15): `KEY_FRAME_RATE` and `Surface.setFrameRate()` do **not** throttle composition, so **Kotlin throttles to the negotiated stream rate** and Go **paces** a bursty source (0 fps on static content/screen-off is normal; a 39.6 Mbps one-second burst was measured on wake). **In-session adaptation** is limited to `PARAMETER_KEY_VIDEO_BITRATE` (applies, but loose — a 6000 → 2000 kbps change settled at ~3.4–3.7 Mbps, ≈1.8× the request, within ~1–2 s) and `REQUEST_SYNC_FRAME` (6–29 ms, p50 ≈ 22 ms); **resolution changes require a new session + new consent** (one VirtualDisplay per projection, single-use tokens, and re-binding a new encoder to a live VirtualDisplay did not resume delivery — 0 frames in two 3 s drains). `KEY_I_FRAME_INTERVAL` counts *configured-fps* frames (1 s @ 30 fps ⇒ a keyframe every 250 ms at 119 fps input), so it must be configured against the real capture rate. Encoder output is `byte[]` handed over the DEC-019 JNI boundary; SPS/PPS was observed in-band as one `CODEC_CONFIG` buffer and the output format exposes `csd-0`/`csd-1` keys (no payload bytes were dumped), so **byte-level framing (Annex-B vs AVCC) is unverified**. **Spike 04 amendments (measured, see [spike 04 evidence](../spikes/04-pion-webrtc-android-linux/)):** `KEY_MAX_FPS_TO_ENCODER=30` is accepted, echoed back in the output format, and **ignored** — encoding stays at ~119.7 fps; the earlier "39.6 Mbps wake burst" is re-measured at 3.0–6.0 Mbps depending on the wake (large post-wake IDR, 107–196 KB), and **frame-rate control is Kotlin/Go responsibility** (see DEC-021). The safe throttle is **GOP-tail dropping** — the encoder stream is IPPP with no B-frames/reordering, so keeping a contiguous prefix of each GOP (IDR + first K AUs) is prediction-safe by construction and verified pixel-exact (SSIM = 1.000000, 0 imperfect frames) — naive 1-of-4 striding is NOT safe (93.3% of kept P-frames corrupted, mean SSIM 0.9504, while ffmpeg concealed it with zero decoder errors). Byte-level framing is now verified: **Annex-B**; SPS/PPS do NOT ride every IDR in-band (measured: 1 of 57,464 AUs carried parameter sets) — parameter-set handling is a transport obligation (see DEC-021). GOP lever: `GOP_aus = KEY_I_FRAME_INTERVAL × KEY_FRAME_RATE` (verified 15/30/60/240); `KEY_FRAME_RATE` does not throttle the encode rate. | `CONFIRMED` (Phase 0) — capture pipeline measured on a single mid-range SoC (SM7475); Spike 04 resolved Kotlin throttling, Go pacing, framing, CSD handoff and wake bursts; HEVC encode path remains unmeasured |
| DEC-021 | Android H.264 transport over Pion WebRTC | **Kotlin capture/encode → bounded AU queue → single-writer send loop → RFC 6184 packetization (single NALU / FU-A, 1200 B) → RTP (90 kHz timestamps = MediaCodec PTS, no base reset) → Pion ICE/DTLS/SRTP** (Spike 04; evidence: [VALIDATION.md](../spikes/04-pion-webrtc-android-linux/VALIDATION.md), [GOP-RETUNE.md](../spikes/04-pion-webrtc-android-linux/GOP-RETUNE.md), [BURST-AND-PSI.md](../spikes/04-pion-webrtc-android-linux/BURST-AND-PSI.md)). Validated: 30-min 720p30 soak byte-exact (57,464 AUs sender = receiver, 207,493 packets, 0 seq gaps/dup/late/ts-backward, 0 decoder errors), CPU 88.7% of one core, native PSS flat (+103 KB), thermal status NONE. **Three transport obligations with measured provenance:** (1) **Burst shaping**: token bucket at the RTP emission point, per-packet, before sequence assignment (ordering/timestamps/markers/FU-A/IDR integrity preserved by construction). Parameters: 4 Mbps ceiling, 3000 kbit bucket, 500 ms idle-credit cap. Unshaped wake bursts peaked 335–648 pkt/s (3.0–6.0 Mbps) and lost 0–44 packets (1 of 3 recent trials lost 12, producing 2 hard decoder errors); shaped: 0 loss in 3/3, peak clamped ≤417 pkt/s, p50/p90 delay unchanged, worst-case hold bounded ≈0.9 s (measured max 584.5 ms from a 195 KB post-wake IDR). (2) **SPS/PPS re-injection**: cache CSD (SPS 18 B / PPS 5 B on SM7475) and prepend to every forwarded IDR lacking them — without this, late join/reconnect/first-AU loss is undecodable (1 of 57,464 AUs carried parameter sets); verified on the wire (every IDR carries SPS+PPS) and by decode, ≈0.3% overhead at 2.5 Mbps. (3) **Frame-rate throttling is NOT encoder capability**: `KEY_MAX_FPS_TO_ENCODER` ignored (amends DEC-020); Kotlin drops prediction-unsafe frames (GOP-tail) and Go paces. **Measured operating point (candidate, not universal):** GOP 30 (`KEY_FRAME_RATE=30`, `KEY_I_FRAME_INTERVAL=1`), GOP-tail keep 8/30 → ~32 AU/s delivered, motion ~59 ms then freeze ~192 ms per 250 ms GOP (cadence set by GOP length: 100–1511 ms freeze across GOP 15–240). **Unmeasured / limitations:** absolute one-way delay (RTP ts = sender CLOCK_MONOTONIC; no clock anchoring — only excess-over-best-case is measurable: p50 17.25 / p99 80.87 ms over the soak); single device/SoC/encoder (Xiaomi 23049PCD8I, SM7475, `c2.qti.avc.encoder`, Android 15, one Wi-Fi path); no cross-vendor evidence; signaling was spike-local HTTP (production signaling elsewhere); data-channel RTT not wired end-to-end. | `CONFIRMED` (Phase 0, Spike 04) — transport obligations ratified for the tested device; DEC-021 parameters are provenance-tracked measurements, not guarantees; cross-device validation and clock-anchored latency remain open |
