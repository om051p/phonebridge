| DEC-020 | Android screen capture pipeline | **MediaProjection → VirtualDisplay → codec input `Surface` → hardware H.264 `MediaCodec` (byte-buffer output) → JNI (`byte[]`) → Go core** (Spike 03 ratified; evidence: [results](spikes/03-android-mediaprojection-encoder-results.md)). **Bootstrap order is consent-first:** Activity `createScreenCaptureIntent()` → foreground service (`type=mediaProjection`) → `getMediaProjection` + `registerCallback` → `createVirtualDisplay`; starting the FGS before consent throws `SecurityException` on Android 15 at **both** targetSdk 34 and 35 (appop `project_media`, which only consent grants, is the gate). **Capture scope is requested explicitly** — the Android 15 dialog defaults to "A single app", so full-screen mirroring requires selecting "Entire screen" (`dumpsys media_projection`: `TYPE_SCREEN_CAPTURE`). **Codec chosen by capability** (`isHardwareAccelerated` + `areSizeAndRateSupported`), H.264 High primary (`c2.qti.avc.encoder` class), HEVC optional (present but unmeasured), **AV1 excluded** (software-only ≤ 1920 px on target devices). **Capture is damage-driven at panel refresh** (119–120 fps measured at 1080×2400 on SM7475/Android 15): `KEY_FRAME_RATE` and `Surface.setFrameRate()` do **not** throttle composition, so **Kotlin throttles to the negotiated stream rate** and Go **paces** a bursty source (0 fps on static content/screen-off is normal; a 39.6 Mbps one-second burst was measured on wake). **In-session adaptation** is limited to `PARAMETER_KEY_VIDEO_BITRATE` (applies, but loose — a 6000 → 2000 kbps change settled at ~3.4–3.7 Mbps, ≈1.8× the request, within ~1–2 s) and `REQUEST_SYNC_FRAME` (6–29 ms, p50 ≈ 22 ms); **resolution changes require a new session + new consent** (one VirtualDisplay per projection, single-use tokens, and re-binding a new encoder to a live VirtualDisplay did not resume delivery — 0 frames in two 3 s drains). `KEY_I_FRAME_INTERVAL` counts *configured-fps* frames (1 s @ 30 fps ⇒ a keyframe every 250 ms at 119 fps input), so it must be configured against the real capture rate. Encoder output is `byte[]` handed over the DEC-019 JNI boundary; SPS/PPS was observed in-band as one `CODEC_CONFIG` buffer and the output format exposes `csd-0`/`csd-1` keys (no payload bytes were dumped), so **byte-level framing (Annex-B vs AVCC) is unverified**. **Spike 04 amendments (measured, see [spike 04 evidence](../spikes/04-pion-webrtc-android-linux/)):** `KEY_MAX_FPS_TO_ENCODER=30` is accepted, echoed back in the output format, and **ignored** — encoding stays at ~119.7 fps; the earlier "39.6 Mbps wake burst" is re-measured at 3.0–6.0 Mbps depending on the wake (large post-wake IDR, 107–196 KB), and **frame-rate control is Kotlin/Go responsibility** (see DEC-021). The safe throttle is **GOP-tail dropping** — the encoder stream is IPPP with no B-frames/reordering, so keeping a contiguous prefix of each GOP (IDR + first K AUs) is prediction-safe by construction and verified pixel-exact (SSIM = 1.000000, 0 imperfect frames) — naive 1-of-4 striding is NOT safe (93.3% of kept P-frames corrupted, mean SSIM 0.9504, while ffmpeg concealed it with zero decoder errors). Byte-level framing is now verified: **Annex-B**; SPS/PPS do NOT ride every IDR in-band (measured: 1 of 57,464 AUs carried parameter sets) — parameter-set handling is a transport obligation (see DEC-021). GOP lever: `GOP_aus = KEY_I_FRAME_INTERVAL × KEY_FRAME_RATE` (verified 15/30/60/240); `KEY_FRAME_RATE` does not throttle the encode rate. | `CONFIRMED` (Phase 0) — capture pipeline measured on a single mid-range SoC (SM7475); Spike 04 resolved Kotlin throttling, Go pacing, framing, CSD handoff and wake bursts; HEVC encode path remains unmeasured |
| DEC-021 | Android H.264 transport over Pion WebRTC | **Kotlin capture/encode → bounded AU queue → single-writer send loop → RFC 6184 packetization (single NALU / FU-A, 1200 B) → RTP (90 kHz timestamps = MediaCodec PTS, no base reset) → Pion ICE/DTLS/SRTP** (Spike 04; evidence: [VALIDATION.md](../spikes/04-pion-webrtc-android-linux/VALIDATION.md), [GOP-RETUNE.md](../spikes/04-pion-webrtc-android-linux/GOP-RETUNE.md), [BURST-AND-PSI.md](../spikes/04-pion-webrtc-android-linux/BURST-AND-PSI.md)). Validated: 30-min 720p30 soak byte-exact (57,464 AUs sender = receiver, 207,493 packets, 0 seq gaps/dup/late/ts-backward, 0 decoder errors), CPU 88.7% of one core, native PSS flat (+103 KB), thermal status NONE. **Three transport obligations with measured provenance:** (1) **Burst shaping**: token bucket at the RTP emission point, per-packet, before sequence assignment (ordering/timestamps/markers/FU-A/IDR integrity preserved by construction). Parameters: 4 Mbps ceiling, 3000 kbit bucket, 500 ms idle-credit cap. Unshaped wake bursts peaked 335–648 pkt/s (3.0–6.0 Mbps) and lost 0–44 packets (1 of 3 recent trials lost 12, producing 2 hard decoder errors); shaped: 0 loss in 3/3, peak clamped ≤417 pkt/s, p50/p90 delay unchanged, worst-case hold bounded ≈0.9 s (measured max 584.5 ms from a 195 KB post-wake IDR). (2) **SPS/PPS re-injection**: cache CSD (SPS 18 B / PPS 5 B on SM7475) and prepend to every forwarded IDR lacking them — without this, late join/reconnect/first-AU loss is undecodable (1 of 57,464 AUs carried parameter sets); verified on the wire (every IDR carries SPS+PPS) and by decode, ≈0.3% overhead at 2.5 Mbps. (3) **Frame-rate throttling is NOT encoder capability**: `KEY_MAX_FPS_TO_ENCODER` ignored (amends DEC-020); Kotlin drops prediction-unsafe frames (GOP-tail) and Go paces. **Measured operating point (candidate, not universal):** GOP 30 (`KEY_FRAME_RATE=30`, `KEY_I_FRAME_INTERVAL=1`), GOP-tail keep 8/30 → ~32 AU/s delivered, motion ~59 ms then freeze ~192 ms per 250 ms GOP (cadence set by GOP length: 100–1511 ms freeze across GOP 15–240). **Unmeasured / limitations:** absolute one-way delay (RTP ts = sender CLOCK_MONOTONIC; no clock anchoring — only excess-over-best-case is measurable: p50 17.25 / p99 80.87 ms over the soak); single device/SoC/encoder (Xiaomi 23049PCD8I, SM7475, `c2.qti.avc.encoder`, Android 15, one Wi-Fi path); no cross-vendor evidence; signaling was spike-local HTTP (production signaling elsewhere); data-channel RTT not wired end-to-end. | `CONFIRMED` (Phase 0, Spike 04) — transport obligations ratified for the tested device; DEC-021 parameters are provenance-tracked measurements, not guarantees; cross-device validation and clock-anchored latency remain open |
| DEC-022 | Production LAN session contract | **The phone's LAN HTTP signaling endpoint is the first ratified production signaling interface, and screen sessions negotiate media parameters before any media starts** (Phase 2 closure). Transport: `POST http://<phone>:<port>/session/{offer,answer,stop}` (default port 7804) carrying the existing authenticated header set (HMAC over the body + nonce anti-replay, validated by `AuthValidator`). **The phone stays the SDP offerer** because Android needs a MediaProjection consent before capture exists (DEC-020), so the geometry must be settled *before* the offer is composed; a data-channel exchange after DTLS is established would arrive too late. **Contract:** (1) the offer request carries the initiator's `MediaParams` (JSON projection of `phonebridge.v1.ScreenStart`); (2) the offer response carries `accepted`, `reject_reason` and the `actual` `MediaParams`, and the **capture device is authoritative** — an `actual` that differs from the request is a *reported downgrade, never a silent substitution*; (3) a request that cannot be met fails typed (`CODE_UNSUPPORTED_MEDIA_PARAMS`) instead of substituting a stream; (4) the `DeviceHello` handshake (`VersionNegotiation` + `CapabilitySet` + `MediaCapabilities`) is exchanged before media, and no common version fails typed (`CODE_INCOMPATIBLE_VERSION`) with no partial session; (5) one active session per device (`CODE_SESSION_BUSY`). **Reconnect is transport-only:** a dropped ICE/DTLS connection re-runs the same offer/answer exchange under the **same session id** while reusing the live MediaProjection/VirtualDisplay/encoder — DEC-020 records that re-binding a new encoder to a live VirtualDisplay does not resume delivery and that resolution changes need a new consent, so capture is never restarted; SPS/PPS re-injection (DEC-021) makes the following IDR decodable immediately. Recovery is bounded (backoff 500 ms → 1 s → 2 s → 4 s, cap 5 s, window 15 s) and exhausting it is classified distinctly (`SESSION_REASON_RECONNECT_TIMEOUT`, never conflated with a transport failure); consent withdrawal is reported typed (`CODE_CONSENT_REVOKED`) rather than appearing as a 0-fps stall. **Scope limits:** LAN-only (no NAT traversal — remote/TURN stays Spike 10), no rendezvous server (`server/` stays Phase 4), and `ScreenStart`/`ScreenStop` are the canonical form of this exchange while the WebRTC data channel is not yet a carrier (DEC-021 records data-channel RTT as unwired). | `CONFIRMED` (Phase 2) — LAN-first slice; remote/TURN and server-based rendezvous remain open |
| DEC-023 | Linux & Android clipboard synchronization architecture | **Wayland `zwlr_data_control_unstable_v1` v2 via decoupled C subprocess helper (`phonebridge-wayland-helper`) on Linux (CONDITIONAL on `COSMIC_DATA_CONTROL_ENABLED=1`), companion `InputMethodService` on Android (CONDITIONAL on `mVisibleBound=true`), centralized Go core synchronization engine (`core/pkg/clipboard`) with SHA-256 echo suppression, and 768 KiB payload ceiling** (Phase 3 closure; evidence: [Spike 05 results](spikes/05-android-clipboard-background-results.md), [Spike 06 results](spikes/06-cosmic-clipboard-results.md)). **Linux platform mechanism:** `zwlr_data_control_unstable_v1` v2 provides 100% focus-independent read/write/observation (215–333 µs) without seat focus, X11 fallback, or window mapping. **Compositor gating:** `cosmic-comp` (Smithay) gates `zwlr_data_control_manager_v1` behind `COSMIC_DATA_CONTROL_ENABLED=1`; daemon pre-flight must verify the variable and report typed code `CLIPBOARD_STATUS_COSMIC_FLAG_REQUIRED` with remediation instructions if missing. **Portal excluded:** Upstream `xdg-desktop-portal` and `xdg-desktop-portal-cosmic` implement NO clipboard interfaces (`org.freedesktop.portal.Clipboard` absent). **Go boundary:** Pure Go core (`CGO_ENABLED=0`); standalone helper binary (~35 KB, 2.4 MB RSS, 0.0% CPU, 304 µs spawn) driven over stdin/stdout pipes (`EVENT=`/`COMMAND=`), isolating the Go supervisor from compositor crashes with bounded backoff restart (500 ms → 1 s → 2 s → 4 s, cap 5 s). **Android mechanism:** Two-tier architecture: (1) Default companion IME (`InputMethodService`) provides ambient background reads (1.0–2.2 ms) and listener callbacks (5.4 ms mean) with hidden keyboard (`mInputShown=false`), **conditional on `mVisibleBound=true`** (active `InputConnection` in foreground window); (2) Manual fallback (Quick Settings Tile / In-App pull) when dormant (`mVisibleBound=false`). Background writes are unconditional (0.7–4.6 ms). **Synchronization architecture:** Platform adapters emit/receive raw clips; pure Go core (`core/pkg/clipboard`) owns state, MIME normalization, payload bounding, and WebRTC DataChannel transport (`phonebridge.v1.ClipboardUpdate`). Because Wayland selection clears immediately on writer process termination (pull-based transience), the Linux Go daemon maintains an in-memory clipboard cache to serve desktop paste requests. **Echo/loop suppression:** Neither Wayland nor Android protocol exposes writer identity; Go core maintains a thread-safe LRU hash ring buffer (capacity 32, TTL 5,000 ms) of recent outbound SHA-256 digests; incoming events matching cached digests within TTL are dropped at the boundary (0 echo cycles proven). **Payload & MIME policy:** PhoneBridge application safety limit: strictly enforces **768 KiB ceiling (786,432 bytes)** on `ClipboardUpdate.payload` bytes, an application-level safety limit informed by Android Binder transaction buffer measurements (where payloads exceeding ~800 KiB risk fatal `TransactionTooLargeException` process crashes). If payload > 786,432 bytes, `ClipboardUpdate` MUST NOT be transmitted; the Go clipboard engine rejects the oversized payload and informs the local UI. File transfer through DEC-012 requires explicit user action; clipboard sync NEVER silently converts into a file transfer. V1 MIME scope: `text/plain;charset=utf-8` and `text/plain`; V1.1: `text/html` and `text/uri-list`. **Security & privacy:** Wire encrypted via WebRTC DTLS/SRTP (DEC-006/DEC-021); local IPC protected by UID peer creds + bearer token (DEC-018); **Zero Logging Rule**: raw clipboard payloads are NEVER logged (only byte counts, MIME types, and 32-bit hex digests). **Flatpak constraint:** Sandboxed Flatpak access succeeds under default Pop!_OS 24.04 but is blocked if `COSMIC_ENABLE_WAYLAND_SECURITY=1` is enforced; native packaging (`.deb` / systemd user service) is primary distribution target. **Reconnect & conflict arbitration:** Transport-only resumption (DEC-022) over a dedicated reliable ordered WebRTC DataChannel (`"clipboard"`, gated by `CAPABILITY_CLIPBOARD`). When the DataChannel opens, both peers exchange their active clip via `ClipboardUpdate`. If the 32-byte `sha256_digest` matches, no write occurs and sync is complete. If digests differ, peers compare `copied_at_ms`: if one timestamp is > 1000 ms newer, the newer clipboard wins; if timestamps differ by <= 1000 ms (or are equal), Linux/Desktop wins as a deterministic tie-breaker. This application-level arbitration rule resolves divergent offline edits without assuming synchronized clocks and requires no separate sync message. | `CONFIRMED` (Phase 3) — CONDITIONAL on Linux `COSMIC_DATA_CONTROL_ENABLED=1` and Android `mVisibleBound=true`; multi-seat and GNOME Wayland fallback remain open |
